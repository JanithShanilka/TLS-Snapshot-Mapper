## 2. Proposed name and research aim

Proposed working name: TLS Snapshot Mapper. Descriptive title: Blind TLS 1.3 Secret Recovery and Role Assignment from Saved Firefox Memory. The aim is to recover the correct application traffic secret for each connection and direction from one saved Firefox/NSS core and its complete PCAP, without known payload markers or reference-secret access during recovery. The current blind experiments target generation-zero 48-byte application secrets for TLS_AES_256_GCM_SHA384. They do not establish recovery of all TLS keys, every browser, or arbitrary incomplete captures. Earlier KeyUpdate and resumption evidence belongs to a separate controlled study. Sources: TLS13_BLIND_STUDY_RESULTS.md; TLS13_ISOLATED_VALIDATION_PLAN.md; TLS13_PRIOR_WORK_MATRIX.md. The name is a proposal, not a novelty or naming-availability claim.

## 3. The path we followed

The path is not a claim that each step invented a new technique. We first learned how to capture and analyze memory independently, then checked whether the idea was already established. TLS 1.3 scenario experiments showed feasibility but still used controlled markers. The later blind study removed these hints. The current phases address stronger comparisons, isolation and transfer. The isolated replay reuses the blind study data. ## 4. Four ideas before the experiments

TLS protects traffic while it travels. A running endpoint must hold usable cryptographic material for its own traffic. A core is a saved image of one process, not necessarily the entire machine's RAM. A PCAP is saved network traffic. A candidate is a possible secret, and the reference is the independent answer held by the evaluator. Possessing privileged access to endpoint memory is essential to this lab method. We are not breaking the cryptographic algorithm. Sources: Attached papers: Baier et al. (2024), doi:10.1016/j.fsidi.2024.301766; Moriconi et al. (2024), X-Ray-TLS, publi-7588.pdf; Baier & Lambertz (2025), doi:10.1016/j.fsidi.2025.301975; Baier & Lengersdorff (2026), doi:10.1145/3785318.3785321.

## 5. Our starting experiment

We used a controlled Firefox session, saved its process memory and traffic, and analyzed the saved copy later. The server separately recorded a reference secret. Recovery did not receive that reference. Only after selecting and sealing a candidate did the evaluator compare it with the answer. This separation is like taking a test before looking at the marking scheme. Capturing the right process required checking actual connection ownership. ## 6. How the client and server exchange data

This is a simplified full TLS 1.3 handshake and application-data diagram, with no 0-RTT or client certificate. ClientHello and ServerHello carry negotiation and public key shares, not plaintext application secrets. Both endpoints derive the matching directional application secrets. After ServerHello, most handshake messages are encrypted. The certificate authenticates the server in normal TLS; the temporary certificate exception in the early localhost lab is documented separately. A client application secret derives a key and IV for client-to-server records, and the server application secret does the same for the reverse direction. ## 10. The evidence has three separate stages

Candidate discovery reads saved memory and emits possible values. Packet-assisted selection uses saved encrypted records to choose the correct value and role. Independent verification opens the protected reference after outputs are fixed, compares exact bytes, and checks negative controls. A match found by searching for a known reference does not count as independent recovery. Neither does a tied memory ranking count as unique selection. This separation carries through the later TLS 1.3 work. Source: lab/offline_memory/README.md; docs/offline-memory/TLS13_BLIND_STUDY_RESULTS.md; lab/blind_tls13/README.md.

## 12. The papers changed our research question

The literature did not prove there were no gaps anywhere. It showed that broad claims such as extracting TLS secrets or studying memory timing were already established. The 2024 survey maps techniques and challenges. X-Ray-TLS uses live event timing and before/after memory changes. TLSKeyHunter finds derivation functions and uses live hooks. Keys in Flux investigates implementation-dependent secret lifetimes. These inputs and objectives differ from blind recovery from a single saved image. Sources: Attached papers: Baier et al. ## 13. Original TLSKeyHunter workflow

Conceptual redraw of the published TLSKeyHunter workflow. Static analysis uses Ghidra and TLS label references to locate PRF/HKDF derivation functions, then emits Key-Derivation Fingerprints. A library-specific Frida script locates the corresponding function in a live target and intercepts its output. Argument positions and structures depend on the library. Extracted secrets and client-random association support traffic decryption. TLS-KeyGround is the authors' validation dataset, not a module of our saved-image recovery. The original Java analyzer, Frida extraction and network_decryption/randomInverse.py remain upstream attribution. Our active recovery does not call this live-hook path. Earlier local live-hook ranker benchmarks are retired provenance and excluded from the active thesis. Sources: supplied TLSKeyHunter paper sections 4–5, https://doi.org/10.1016/j.fsidi.2025.301975; docs/UPSTREAM_README.md; root README.md and active THESIS_SCOPE.md.

## 14. Keys in Flux: measuring secret lifetimes

Conceptual redraw of Keys in Flux's measurement method, not a reproduction of its experiments. A KDF hook records key creation, value, address, length and context. Hardware watchpoints observe writes to the original buffer. Protocol-state-triggered full process dumps are searched for every copy of the already-observed secret. Watchpoint overwrite alone is insufficient to establish complete removal. Peer-exported keys validate the observed key, and PCAPs align observations with protocol states. Together these measurements reconstruct start/end of life. This study concerns presence and lifetime with instrumentation, not blind discovery of unknown values from one saved image. We use it to motivate explicit acquisition state and restrained generalization. Source: supplied Keys in Flux PDF §4, https://doi.org/10.1145/3785318.3785321.

## 15. X-Ray-TLS: recovery from memory changes

Conceptual redraw of the full X-Ray-TLS method. eBPF maps traffic/socket events to a process and triggers acquisition around the TLS handshake. The process is paused for writable-memory snapshots near handshake start and completion, then resumed. The memory difference narrows the search space. Aligned high-entropy candidate values in the difference are tried against captured traffic using the project's patched TShark. For TLS 1.3 the target is application traffic. Our single retained ELF core cannot supply those live events and paired snapshots. We adapted only the separate full-snapshot entropy baseline in the authors' source, adding our shared assignment stage. Its result must never be labelled a result for full X-Ray-TLS. Source: supplied publi-7588.pdf §3, https://www.eurecom.edu/publication/7588/download/data-publi-7588.pdf; TLS13_PRIOR_WORK_MATRIX.md.

## 17. Why we did not stop at the broad ideas

These papers establish overlapping broad research directions, so simply repeating one is not a sufficient novelty claim. TLSKeyHunter identifies derivation functions and uses live hooks. X-Ray-TLS acquires timed memory snapshots and searches their changes. Keys in Flux measures secret lifetimes across implementations and protocol states. Our decision rationale is synthesized from those published input requirements and the local research scope. It does not claim these papers leave no research gaps. The selected input contract is a single already-saved Firefox image plus its traffic, followed by blind assignment, abstention and measured comparison. Original framework credit remains with its authors.

## 18. Why the question became narrower

The path was driven by evidence, not just by searching for an untouched topic. Memory scores tied, so traffic authentication became necessary. The five-scenario study used controlled markers, so a separate blind study removed known-message hints. The first entropy baseline was bounded and weak, so stronger baselines and a resource grid are needed. Unix permissions were weaker than the intended isolation claim, so the retained data was replayed inside stricter boundaries. Transfer and confirmation remain planned. These connections are an interpretation supported by the documented results and amendments, not an assertion that every decision has a dated quotation in the work log.

## 33. 1. Historical structure + entropy filter

NSS is Firefox's TLS library. In this implementation, the scanner searches an aligned CKA_VALUE attribute with type 0x11, a pointer, and a length field. It reads the buffer through that pointer. The historical ranker scans 32- and 48-byte layouts, and the blind study retains only the 48-byte candidates for its SHA-384 suite. Entropy is a randomness score, not a probability that the candidate is correct. The ranker requires empirical byte entropy of at least 4 bits/byte. A zero-byte count of at most length/8 adds a ranking preference; it is not a mandatory rejection rule in this arm. Values are deduplicated, sorted by score and deterministic ID, and capped before assignment. The frozen wrapper returns no candidates if structured enumeration times out. This behavior differs from arms that retain partial candidates. Sources: lab/offline_memory/rank_tls13.py rank(); lab/blind_tls13/recover.py bounded_structured_rank().

## 34. 2. Structure only

This ablation removes entropy admission while preserving a 48-byte CKA_VALUE pointer/length layout. It checks alignment, type 0x11, a plausible readable pointer and the required length. It reads the pointed-to buffer, deduplicates equal values and retains candidates in enumeration order up to the cap. It makes no entropy or zero-byte admission decision. It keeps candidates found before a timeout, whereas the historical structured wrapper currently returns none on timeout. Thus differences must be attributed to filtering, ordering and timeout behavior as well as discovery. Compare post-seal reference candidate recall to count true secrets removed by the historical filter. This is a diagnostic comparison, not a claim that structure-only search is new.

## 35. 3. Adapted Anderson NSS adjacency

The published NSS adjacency pattern targets a 48-byte master secret, primarily for TLS 1.2. Our implementation explicitly adapts its candidate pattern to 48-byte TLS 1.3 application traffic secrets. It scans for marker bytes 11 00 00 00, checks a 0x30 length at one of two offsets, and reads the following 48 bytes in the pattern. It does not dereference an NSS pointer and does not use entropy admission. Relative to the marker, alternative one has length at offset 12 and value at 16; alternative two has length at 16 and value at 24. Repeated values are deduplicated, and enumeration stops at K or the time budget, retaining partial results. Role assignment is our common stage. Source: TLS13_PRIOR_WORK_MATRIX.md; lab/isolated_tls13/comparators.py anderson_nss_adjacent(); https://arxiv.org/html/1805.11544. This is not a reproduced published TLS 1.3 result.

## 36. 4. Adapted X-Ray full-snapshot baseline

This is an adaptation of X-Ray-TLS's separate full-snapshot entropy baseline, not its main live memory-difference method. It visits writable captured memory, inside 4096-byte pages, using 48-byte windows at 8-byte steps. The original boundary excludes the final possible window in each page and the adaptation preserves that behavior. For each value it computes entropy of 96 hexadecimal characters, requiring at least 3.6 bits per hex character. It deduplicates qualifying values and keeps the best K by that entropy score and digest, replacing lower-ranked values as scanning continues. The original baseline counts candidates; our adaptation retains candidates and adds our shared role-assignment stage. These 3.6 units are not directly comparable to raw-byte entropy 4 in the historical arm. Sources: local X-Ray src/baseline/entropy_filter.py as inspected in TLS13_PRIOR_WORK_MATRIX.md; lab/isolated_tls13/comparators.py xray_full_snapshot_entropy().

## 37. 5. Historical entropy-only search

This historical baseline visits every readable captured ELF load segment, regardless of the writable flag. It examines 48-byte windows at one-byte steps in address order, skipping provably ineligible windows in all-zero pages. A candidate must have at most six zero bytes and empirical raw-byte entropy of at least 4 bits/byte. Deduplication and a bounded top-K heap keep the highest-entropy candidates found so far, with a digest tie-break. It scans until completion or the time limit and then tests retained values. It uses no NSS structure, pointer or adjacency clue. Comparing its outcome with X-Ray's adapted full-snapshot baseline distinguishes regions, scan step, scoring representation and cost; it is not solely a test of one numerical threshold. Source: lab/blind_tls13/recover.py entropy_rank().

## 38. Every method faces the same traffic test

Candidate generation is blind to packets and references. The common stage discovers completed TLS 1.3 handshakes and connection directions from the PCAP. For each candidate and role, it derives the suite-specific record key and IV using HKDF, then checks AEAD record authentication with the appropriate nonce and sequence context. Selection requires one unique candidate to authenticate at least two consecutive application records in the declared generation-zero epoch. Ambiguity, timeout, missing evidence or repeated candidate use across roles produces unresolved decisions. Known payload content is not a selector. Outputs are sealed before the root-only evaluator checks exact reference equality and false assignments. The authentication stage has a separate 300-second budget. ## 40. How the budget grid works

The resource grid predeclares three search-time limits and three candidate caps, making nine settings per method per selected case. The same twenty preselected retained case IDs are used for all settings and all five methods. The full planned grid therefore has 20 × 9 × 5 = 900 method runs, reusing twenty cases; it is not nine hundred new independent cases. The primary retained-corpus comparison uses 180 seconds and 100 candidates. The packet-authentication stage separately allows 300 seconds, so search seconds do not equal end-to-end time. Structural enumeration can stop at K; the historical structured arm enumerates/ranks before trimming, while entropy arms maintain the top K and continue scanning. Preserve the actual cap/timeout behavior in analysis. Historical structured timeout returns no candidates; other arms can retain partial sets. The comparison must record recovery, false assignments, abstention, timeouts, CPU/wall time and memory. No grid outcome is claimed here. Source: TLS13_SENSITIVITY_MANIFEST.json; TLS13_ISOLATED_VALIDATION_PLAN.md; lab/isolated_tls13/sensitivity_study.py.

## 41. What we need to learn next

The primary comparison establishes that entropy admission did not improve complete positive recovery over structure-only on the retained sample at the primary budget. It does not prove entropy is universally unnecessary, and wall-time medians alone are not a significance test. Next we need the sealed resource-grid analysis: candidate recall, which genuine values the filter discards, cap effects, timeouts, ordering, authentication trials and cost. If entropy provides no measured benefit, simplify the method and report that conclusion rather than defend a preferred ranker. Any change becomes a newly declared method; historical evidence remains frozen. Unseen builds and fresh confirmation separately test transfer and repeatability. Final success is a defensible rule with explicit limits and correct abstention, not a forced claim of universal superiority. ## 42. The next phases test generalization

The unseen builds are Firefox 135.0.1 and 137.0.2, with twenty planned cases each: fourteen positives and six controls. Archives and build hashes were pinned before inspecting any transfer outcome. Discovery and assignment rules stay frozen; adaptations become new methods. Fresh confirmation proposes one hundred newly generated cases with seventy positives and thirty controls, separate from development and transfer. Independent verification has one completed integration case that checked twelve payload hashes using recovered application secrets plus reference handshake-only decoder support. That support must be disclosed and a representative subset is still planned. Source: docs/offline-memory/TLS13_ISOLATED_VALIDATION_PLAN.md (2 October 2026).

## 43. What we can honestly say today

The current evidence supports controlled saved-memory recovery and role assignment for the named Firefox/NSS build and cipher suite, documented failed pilots and repairs, a paired five-arm retained-case comparison, and replication on retained data with stricter isolation. The broader novelty and generalization case is unfinished. Do not say TLS is broken, all browsers are supported, memory ranking alone identifies secrets, or the study beats full X-Ray-TLS. Acquisition requires privileged endpoint access, the workload is controlled, complete PCAPs are assumed in the blind study, and temporary lab compatibility exceptions limit the early experiments.
